# 设计说明：Phase 0b fp32 状态对照

状态：已由用户同意（"同意"）。本文件先于代码编写。
关联：`docs/design_phase0b.md`，`experiments/E004_erase_forget_ablation/README.md` 的"bf16 掩盖"限制。

## 1. 目的

E004 的结论是“按键擦除对读出没有可测贡献”。但状态以 bf16 存储，擦除相对于衰减后状态的大小约为 $10^{-5}$，低于 bf16 的相对精度（约 $4\times10^{-3}$）。因此擦除项可能在存储时被舍入掉。本对照检验：**把状态的存储与递推精度提到 fp32，擦除的贡献是否出现。**

## 2. 单一变量

只改变**状态的存储与递推精度**：

- 键、值、门控的线性投影 $W_k,W_v$ 与门控层仍在 bf16 下计算（与原始一致），结果转为 fp32 后参与递推；
- 状态 $M$ 与键的累计状态 $z$ 以 fp32 存储与更新；
- 读出时，把 query 转为 fp32 与 fp32 状态相乘，输出转回 query 原来的 dtype（bf16）；
- 模型的其他部分（backbone、门控参数、读出之后的 o_proj）不变。

这样读出的数据类型与下游接口保持不变，只改变状态的精度。

## 3. 接口

- `src/diagnostics/gate_ablation.py`
  - `gated_delta_update(..., precision="bf16"|"fp32")`：`fp32` 时把投影结果转为 fp32 后递推，状态以 fp32 存储。`bf16` 时行为与当前版本完全一致。
  - `install_mode(model, mode, stats=None, precision="bf16")`：`fp32` 时同时包裹每层 `local_memory.read`（见下）。`mode="original"` 时恢复所有包裹。
  - `install_read_fp32(model)` / `restore_read(model)`：为每层本地记忆的 `read` 设置或取消 fp32 包裹。
- `experiments/E005_fp32_control/`：复用 `run_ablation.py`，新增 `--precision` 参数。

读出包裹的逻辑：
- 状态为 None 时（重置后尚未写入），直接调用原始 `read`，保持原行为；
- 否则调用原始 `read(q.float())`，输出转回 `q.dtype`。

## 4. 度量

- 与 E004 相同：答案 token 的平均 NLL，配对差与 bootstrap 95% 区间，相对 `full`。
- **精度效应**：同一 QA 上 `full`（fp32）减去 E004 的 `full`（bf16）。它量化把精度提到 fp32 本身带来的变化。
- **擦除效应（fp32 下）**：`no_erase`（fp32）减去 `full`（fp32）。这是本对照的主要问题。
- 状态统计：每层擦除相对大小与 $1-\alpha$，与 E004 的 `state_stats_full.csv` 对比。

## 5. 判定规则（预先约定）

- 若 fp32 下 `no_erase` 的 95% 区间仍包含 0，且点估计可忽略：按键擦除在 fp32 下也没有可测贡献。结论升级为“与精度无关”，思路三的按键擦除增量不成立。
- 若 fp32 下 `no_erase` 的区间明显大于 0：E004 的 “无贡献” 是 bf16 掩盖造成的。思路三需要在 fp32 条件下重新评估，且需要确认 bf16 训练时是否也依赖这一效应。
- 精度效应本身很大（例如 $>0.05$ 且区间不含 0）：说明 bf16 状态对 NLL 有实质影响，需要单独报告。

## 6. 单元测试

在 `tests/test_gate_ablation.py` 中增加：

1. `fp32` 模式的状态 dtype 为 float32，且与 float64 参照的误差在 $10^{-5}$ 相对量级以内。
2. 擦除在 fp32 下保留：`full` 与 `no_erase` 的状态差等于擦除项（与 float64 直接计算比较），且非零。
3. 同一擦除量在 bf16 状态下被舍入：把状态先转为 bf16 再做写入，`full` 与 `no_erase` 的差为 0（复现 E004 的现象）。
4. 读出包裹：输出 dtype 与输入 query 相同；与 float64 参照误差小；状态为 None 时不报错。
5. `bf16` 模式的行为与当前版本逐位一致（回归测试，使用参照实现）。

## 7. 真实模型检查

- `fp32` 的 `full` 与原始 bf16 的状态差应为 bf16 量级（非零但小）。脚本只报告该差值，不做逐位断言。
- 对同一会话检查 `no_erase` 与 `full`（fp32）的状态差，确认擦除项在真实模型中出现在状态里（非零）。

## 8. 失效模式与回滚

- **dtype 不一致**：读出与状态相乘时报错。由单元测试捕获。
- **状态 None 的读出**：原始路径会创建 bf16 零状态，之后的写入会被提升为 fp32。已在包裹中处理。
- **显存**：fp32 状态每层 $1024\times1024\times4$ 字节约 4MB，32 层约 128MB，batch 为 1 时可接受。
- **回滚**：包裹通过实例属性实现，`install_mode("original")` 或进程退出即恢复。仓库中的模型代码不改动。
- **异常**：出现 NaN 或发散时停止，不调参掩盖。

## 9. 范围外

- 不改变 Metis 的结构、门控或训练方式。
- 不引入新的记忆机制。
- 不修改数据、指标或划分。
- 不做生成式准确率。

## 10. 计算预算

与 E004 相同：100 个会话，4 种模式，约 10 分钟。
